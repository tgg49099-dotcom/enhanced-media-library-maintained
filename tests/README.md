# tests/ - the compatibility test harness

This directory contains the harness we used to measure and verify the
compatibility patches, plus the **raw output of every run**.

## What is tested

Real WordPress installations (not a mock): WordPress **6.8.12** and **7.1.4**,
each with its own SQLite database, driven by PHP **8.3.29** and **8.5.8**.
Every request is a real HTTP request against a real `php -S` server, with the
plugin's own screens and forms.

| test | what it does |
|---|---|
| T1 | activation of the plugin, no fatal error |
| T2 | public front: a published page with a `[gallery]` and a `[playlist]` shortcode |
| T3 | media library, grid view and list view |
| T4 | media edit screen (the EML taxonomy checklist must be rendered) |
| T5 | saving a media through the **real** edit form (title and description really change) |
| **T6** | **saving a media through the plugin's own AJAX endpoint** `wp_ajax_save-attachment-compat`, on a fresh install where no media category exists yet — **this is the test that can go red** |
| T6b | same endpoint with a `tax_input` payload (the nominal case) |
| T7 | the five settings screens (Media Library, Media Taxonomies, MIME Types, Settings, Media Settings) |
| T8 | saving the settings through the **real** forms of those screens |
| T9 | the utilities: export, import **with** a real JSON file, import **without** a file part |

A test is red when the plugin wrote **any** PHP diagnostic (error, warning,
notice, deprecation) into `wp-content/debug.log` during that step, or when the
step did not do what it is supposed to do.

## The matrix

```
{original, fixed}  x  {WordPress 6.8.12, WordPress 7.1.4}  x  {PHP 8.3.29, PHP 8.5.8}
```

8 cases. They are run **sequentially, on purpose**: WordPress test suites of
this kind are not parallelisable in the same sandbox (two suites fighting over
the same database produce false results).

## Result

| | WP 6.8.12 / PHP 8.3.29 | WP 6.8.12 / PHP 8.5.8 | WP 7.1.4 / PHP 8.3.29 | WP 7.1.4 / PHP 8.5.8 |
|---|---|---|---|---|
| official 2.9.4 | 8 green / **2 red** | 8 green / **2 red** | 8 green / **2 red** | 8 green / **2 red** |
| patched | 10 green / 0 red | 10 green / 0 red | 10 green / 0 red | 10 green / 0 red |

The two red tests on the official code are **T6** (2 warnings) and **T9** (3
warnings). On the patched code the plugin writes **nothing** in the log.

## Files

| file | role |
|---|---|
| `run-matrix.sh` | runs the 8 cases, one after the other, and writes `matrice.txt` |
| `run-case.sh` | runs **one** case: `run-case.sh <original\|fixed> <wp-6.8.12\|wp-7.1.4> <8.3.29\|8.5.8>` |
| `lib.sh` | helpers: PHP binaries, wp-cli wrapper, database reset, diagnostic counter, authentication cookie, server start/stop |
| `setup-env.sh` | creates one isolated WordPress installation (download, SQLite drop-in, `wp core install`) |
| `form-post.py` | turns an HTML form into a browser-like `application/x-www-form-urlencoded` body (checkboxes, hidden "0" twins, `<select>`, `<textarea>`) |
| `apply-compat-patch.py` | rebuilds the patched tree from the official ZIP and checks that **only** the two patched files differ |
| `mutate.py` | removes or restores the compatibility fix, by exact string replacement that refuses to write if the pattern is not found exactly once (`MUT_PATTERN=eml`) |
| `results/matrice.txt` | the summary of the run |
| `results/matrice-2026-11-12.txt` | re-run of the 4 patched cases on 2026-11-12: 4 green, 0 red |
| `results/contre-preuve-rouge.txt` | **the red/green counter-proof: the raw output of the same test on the official code and on the patched code** |
| `results/contre-epreuve-mutation.txt` | **the mutation counter-proof: the same test with the fix removed (RED), then with the fix put back (GREEN)** |
| `results/<case>/` | per case: `console.txt`, `resultats.txt`, `debug.log.plugin-only.txt` |

## Reproducing

```bash
# 1. build the two trees (the official ZIP must be extracted in original/)
python3 apply-compat-patch.py

# 2. create the two WordPress installations (once)
bash setup-env.sh 6.8.12 "$EML_BASE/env/wp-6.8.12" http://127.0.0.1:8092
bash setup-env.sh 7.1.4  "$EML_BASE/env/wp-7.1.4"  http://127.0.0.1:8091

# 3. run the whole matrix (sequential)
bash run-matrix.sh all
```

The harness expects two PHP binaries and a `wp-cli.phar`; the paths can be
overridden with the `EML_PHP_83`, `EML_PHP_85` and `EML_WPCLI` environment
variables (see `lib.sh`).

## A note on the authentication cookies

The tests authenticate as the administrator with cookies generated by WordPress
itself (`wp_generate_auth_cookie()`), not by replaying a browser session. The
nonces used by the plugin's AJAX endpoints are scraped from the HTML of the
screen that owns them (`_wpnonce` on the media edit screen, the
`eml-settings-*-nonce` hidden inputs on the utilities screen), because a nonce
created out of band (for instance with `wp eval`) is bound to another session
token and is therefore rejected by `check_ajax_referer()`.
